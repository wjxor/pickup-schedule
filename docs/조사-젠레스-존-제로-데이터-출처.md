# 조사 기록 — 젠레스 존 제로 데이터 출처

조사일: 2026-08-21
구현 완료: `src/lib/collectors/adapters/hoyolab.ts`

## 결론

**ZZZ에는 원신·스타레일이 쓰는 `getAnnList` 공지 API가 없다.**
대신 HoYoLAB 뉴스 API를 쓰고, 본문에서 기간을 추출한다. LLM 파서는 필요 없다.

---

## 1. 공지 API 탐색 (실패)

원신은 `sg-hk4e-api.hoyoverse.com`, 스타레일은 `sg-hkrpg-api.hoyoverse.com` 에서
`/common/{game_biz}/announcement/api/getAnnList` 로 공지를 받는다.
같은 규칙이라면 ZZZ는 `sg-nap-api.hoyoverse.com` 이어야 하는데, **이 호스트는 DNS에 존재하지 않는다.**

시도한 호스트와 결과:

| 호스트 | DNS | 공지 경로 응답 |
|---|---|---|
| `sg-nap-api.hoyoverse.com` | ❌ 없음 | — |
| `announcement-api.hoyoverse.com` | ❌ 없음 | — |
| `sg-public-api.hoyoverse.com` | ✅ | 404 |
| `sg-hyp-api.hoyoverse.com` | ✅ | 404 |
| `public-operation-nap.hoyoverse.com` | ✅ | 404 |
| `announcement-api.mihoyo.com` | ✅ | `retcode 0` 이지만 목록이 비어 있음 (중국 서버 게이트웨이) |

경로도 `/common/nap_global/announcement/api/getAnnList`, `/common/announcement/api/getAnnList`,
`/announcement/api/getAnnList`, `announcement_api` 변형 등을 시도했으나 전부 404.

`public-operation-nap.hoyoverse.com` 은 ZZZ 전용 호스트가 맞다.
`/common/apicdkey/api/webExchangeCdkey` 는 404가 아니라 `retcode -1071` 을 돌려준다.
즉 이 호스트는 `/common/{서비스}/api/{메서드}` 형태로 라우팅하지만 공지 서비스는 올라와 있지 않다.

## 2. 가챠 캘린더 API (사용 불가)

```
https://sg-act-public-api.hoyolab.com/event/game_record_zzz/api/zzz/gacha_calendar
```

이름 그대로 픽업 배너 일정을 주는 API지만 **로그인이 필요하다.**

```json
{"data":null,"message":"Please log in to take part in the event（-100）","retcode":-100}
```

`game_record` 계열은 HoYoLAB 계정 쿠키와 게임 계정 연동이 전제라 자동 수집에 쓸 수 없다.

## 3. HoYoLAB 뉴스 API (채택)

```
GET https://bbs-api-os.hoyolab.com/community/post/wapi/getNewsList?gids=8&type=1&page_size=30
GET https://bbs-api-os.hoyolab.com/community/post/wapi/getPostFull?post_id={post_id}
```

- 인증 불필요
- `x-rpc-language: ko-kr` 헤더를 넣으면 한국어 제목·본문이 온다
- `gids` 는 게임 식별자다. **2 = 원신, 6 = 스타레일, 8 = ZZZ** (1 = 붕괴3rd)
- `type` 은 **1 = 공지, 2 = 웹이벤트, 3 = 소식**. 기간이 있는 것은 주로 `type=1`

### 주의할 점

- `getNewsList` 의 `content` 는 미리보기라 잘려 있다. 기간을 뽑으려면 `getPostFull` 이 필요하다.
- `getPostFull` 의 본문은 리치 텍스트라 `content` 가 아니라 **`structured_content`** 에 들어 있다.
  JSON 배열이며 `insert` 필드의 문자열을 이어붙이면 평문이 된다.
- `event_start_date` / `event_end_date` 필드가 있지만 **값이 전부 `0`이라 쓸 수 없다.**

## 4. 기간 추출 전략

공지 15건 실측 결과:

| 유형 | 건수 | 처리 |
|---|---|---|
| 절대 날짜 `2026/08/19 13:00(KST) ~ 2026/09/08 15:59(KST)` | 8 | 정규식 |
| 시작만 상대 `버전 업데이트 후 ~ 2026/09/07 04:59(KST)` | 2 | 버전 기간표로 치환 |
| 완전 상대 `3.1 버전 업데이트 후 ~ 3.1 버전 종료 전` | 2 | 버전 기간표로 치환 |
| 기간 없음 (영구 추가 콘텐츠, FAQ) | 3 | `endAt = null` 이 정답 |

**버전 기간표를 먼저 만드는 것이 핵심이다.**
버전 업데이트 공지는 절대 날짜를 준다.

> `3.1 버전 「기나긴 이별」 업데이트 공지` → `2026/08/19 13:00 ~ 2026/09/09 06:59`

이 값을 버전별로 모아두면 `3.1 버전 업데이트 후`, `3.1 버전 종료 전` 같은 표현을
전부 절대 시각으로 바꿀 수 있다. 그래서 LLM 파서 없이 처리된다.

시각 표기에 `(KST)` 가 명시돼 있어 타임존 추측이 필요 없다.

## 5. 분류 키워드

ZZZ의 가챠는 **「변조」**(Modulation), 배너는 **「기간 한정 채널」** 이라고 부른다.
`src/lib/collectors/adapters/hoyoverse.ts` 의 `classifyHoyoAnnouncement` 에 있는
기존 키워드(기원 / 워프 / 조율)로는 잡히지 않으므로 `변조`, `채널` 을 추가해야 한다.

## 6. 구현 결과

`src/lib/collectors/adapters/hoyolab.ts` 로 구현했다. 실제 수집 결과는 30건 중
23건이 기간을 확보했고, 나머지 7건은 본문에 기간이 없는 공지(영구 콘텐츠, FAQ)라
게시일을 시작으로 두고 종료는 `null` 로 남긴다.

### 구현하면서 알게 된 것

**이미지는 `post` 바깥에 있다.**
`post.cover` 와 `post.images` 는 대부분 비어 있다. 실제 이미지는 목록 항목의
`image_list[0].url` 에 들어 있다. 이걸 모르고 `post` 안만 보다가 이미지가 0건으로
수집됐다.

**사전 다운로드 공지의 종료 시각이 버전 시작이다.**
버전 기간표를 만들 때 처음에는 같은 버전 공지들의 가장 넓은 구간을 썼는데,
「3.1 버전 사전 다운로드 오픈」 공지의 기간이 `07/27 13:00 ~ 07/29 06:50` 이라
버전 시작이 07/27 로 잡혔다. 이 공지의 기간은 "다운로드가 열린 시각 ~ 점검 종료"라서
**끝나는 쪽**이 새 버전의 시작이다. 이렇게 고치자 3.0 버전 종료(`07/29 06:59`)와
3.1 버전 시작(`07/29 06:50`)이 정확히 맞물렸다.

### 계획에서 바꾼 것

새 글만 골라 본문을 받는 최적화는 넣지 않았다. 하루 30건 규모라 절약폭이 크지 않고,
매번 다시 받으면 게임사가 나중에 정정한 기간까지 반영된다는 이점이 있다.
대신 요청 사이에 300ms 간격을 둔다.

### 재사용

이 어댑터는 `gids` 만 바꾸면 원신(2)·스타레일(6)·붕괴3rd(1)에도 그대로 쓸 수 있다.
호요버스 공지 API가 막히는 날의 폴백 경로가 된다.
