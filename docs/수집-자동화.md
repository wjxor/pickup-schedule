# 수집 자동화 설정

GitHub Actions로 일정 수집을 하루 4번 자동 실행한다.
워크플로 정의는 [`.github/workflows/collect.yml`](../.github/workflows/collect.yml) 에 있다.

## 왜 필요한가

호요버스 공지 API와 HoYoLAB 뉴스 API는 **현재 진행 중이거나 곧 시작하는 공지만** 내려준다.
과거 이력이 없다.

즉 수집을 거른 사이에 시작해서 끝난 짧은 이벤트는 **영영 남지 않는다.**
"지난주에 어떤 픽업이 있었지?"에 답하려면 매일 받아서 우리 DB에 쌓는 수밖에 없다.

## 실행 주기

| cron (UTC) | 한국시간 | 노린 것 |
|---|---|---|
| `0 21 * * *` | 06:00 | 게임 점검 종료 직후. 새 버전·픽업이 이때 열린다 |
| `0 3 * * *` | 12:00 | 낮 공지 |
| `0 9 * * *` | 18:00 | 저녁 공지 |
| `0 15 * * *` | 24:00 | 마감 |

한 번 실행에 외부 API 요청은 40여 회다. 하루 4번이면 160여 회로, 상대 서버에 부담되는 양이 아니다.

---

## 1단계 — GitHub Secrets 등록

**이 작업은 직접 해야 한다.** 비밀키를 다루기 때문이다.

1. 저장소 페이지에서 **Settings** → 왼쪽 메뉴 **Secrets and variables** → **Actions**
2. **New repository secret** 을 눌러 아래 두 개를 등록한다.

| Name | Secret 값 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `.env.local` 의 같은 이름 값 |
| `SUPABASE_SERVICE_ROLE_KEY` | `.env.local` 의 같은 이름 값 |

`NEXT_PUBLIC_SUPABASE_ANON_KEY` 는 필요 없다. 수집기는 쓰기만 하므로 `service_role` 키만 쓴다.

> **주의**
> 저장소가 공개라도 Secrets 값은 공개되지 않는다. 로그에 찍히면 GitHub가 자동으로 가려준다.
> 다만 워크플로 파일에 값을 직접 적으면 그대로 노출되므로, 반드시 `${{ secrets.이름 }}` 형태로만 참조한다.

## 2단계 — 워크플로를 기본 브랜치에 올리기

**이걸 먼저 해야 Actions 탭에 워크플로가 나타난다.**

GitHub Actions는 저장소에 실제로 올라와 있는 워크플로만 인식한다.
로컬에만 있으면 Actions 탭 왼쪽 목록이 비어 있다.

또한 **`Run workflow` 버튼은 워크플로가 기본 브랜치(`main`)에 있을 때만** 나타난다.
기능 브랜치에만 올리면 예약 실행도 되지 않고 수동 실행 버튼도 보이지 않는다.

```bash
git switch main
git merge --no-ff feature/collect-automation
git push
```

푸시하고 나면 Actions 탭에 **일정 수집** 이 보인다.

## 3단계 — 수동 실행으로 확인

스케줄을 기다리지 말고 먼저 한 번 돌려본다.

1. 저장소 페이지 상단 **Actions** 탭
2. 왼쪽 목록에서 **일정 수집** 선택
3. 오른쪽 **Run workflow** → 브랜치 `main` 확인 후 **Run workflow**

1~2분 뒤 결과를 확인한다. 로그에 이런 줄이 보이면 정상이다.

```
INFO: 수집 완료  game: "원신"  count: 28
INFO: DB 저장 완료  저장됨: 121  건너뜀: 0  실패: 0
```

로컬에서도 건수를 확인할 수 있다.

```bash
npm run db:check
```

## 4단계 — 실패 시

워크플로가 실패하면 GitHub가 저장소 소유자에게 메일을 보낸다.
Actions 탭에서 로그를 열어 원인을 본다.

| 로그 메시지 | 원인 | 해결 |
|---|---|---|
| `Supabase 환경변수가 없습니다` | Secrets 미등록 또는 이름 오타 | 1단계 확인 |
| `Invalid API key` | 키 값이 잘못됨 | Supabase 대시보드에서 다시 복사 |
| `수집 건너뜀 ... HTTP 4xx` | 게임사 API 스펙 변경 가능성 | 해당 어댑터 점검 |
| `events upsert 실패` | 스키마 불일치 | 마이그레이션 적용 상태 확인 |

한 게임이 실패해도 나머지 게임 수집은 계속된다.
어댑터가 예외를 던지지 않고 건너뛴 이유를 로그에 남기도록 만들어져 있기 때문이다.

## 알아둘 점

**60일 규칙**
공개 저장소에서 60일 동안 아무 커밋도 없으면 GitHub가 예약 실행을 자동으로 중단한다.
중단되면 메일이 오고, Actions 탭에서 다시 켤 수 있다.
개발이 계속되는 동안은 신경 쓸 일이 없다.

**예약 실행은 정시에 오지 않는다**
GitHub Actions의 cron은 부하가 몰리면 수십 분씩 밀린다. 아예 건너뛰기도 한다.
분 단위 정확도가 필요한 작업에는 쓰면 안 되지만, 하루 4번 일정을 긁는 용도에는 문제없다.

**중복 걱정은 없다**
`(game_slug, external_id)` 기준 upsert라 같은 공지를 몇 번 다시 받아도 덮어쓰기만 된다.
오히려 다시 받는 편이 게임사가 나중에 정정한 기간까지 반영해 준다.

## 대안 — Vercel Cron

앱을 Vercel에 배포한 뒤에는 Vercel Cron으로 옮겨도 된다.
API Route를 만들고 `vercel.json` 에 스케줄을 적는 방식이다.

지금 GitHub Actions를 택한 이유는 배포 전에도 바로 쓸 수 있고,
실패 시 로그와 알림이 저장소 안에서 함께 관리되기 때문이다.
