### 4. 데이터 수집 방식에 대한 문제 제기

> 게임 픽업과 스케쥴 일정을 API로 못불러오는거 아니야? 이 문제는 해결하기 위해 내 답변 보고 다시 물어봐줘

**이 지적이 설계를 바꿨다.**

레퍼런스 사이트가 크롤링을 쓴다는 이유로 크롤링을 전제하고 있었으나,
실제로 후보 엔드포인트를 호출해 검증한 결과 공식 API가 존재했다.

| 게임 | 검증 결과 |
|---|---|
| 원신 | HTTP 200 — 시작일·종료일·배너까지 구조화 제공 |
| 붕괴: 스타레일 | HTTP 200 — 동일 스키마 |
| 림버스 컴퍼니 | HTTP 200 — Steam 공식 Web API |
| 젠레스 존 제로 | 게이트웨이 호스트 미확정 |
| 니케 / 명조 | 공개 API 없음 |

"모든 공지를 LLM으로 파싱한다"는 초기 계획은 과잉 설계였고,
LLM 파서가 필요한 범위가 6종 중 2종으로 축소됐다.

### 5. 지원 게임 범위 확정

> 게임은 원신, 붕괴:스타레일, 승리의 여신:니케, 명조:워더링 웨이브, 젠레스 존 제로, 림버스 컴퍼니 할거야
> 추후에 추가할수도 있어

"추후 추가" 요구를 반영해 게임 레지스트리(SSOT) + 어댑터 플러그인 구조로 설계.
게임 추가 시 레지스트리 항목 하나만 넣으면 UI 필터·색상·정렬이 자동 반영된다.

### 6. 라이브러리 문서 확인 지침

> context7은 준수해

Next.js 16, Tailwind CSS v4, Zod 4의 최신 API를 context7로 확인 후 코드 작성.

- Next 16: `params` / `searchParams`가 Promise로 변경됨
- Tailwind v4: `@theme` CSS-first 설정
- Zod 4: `z.string().datetime()` deprecated → `z.iso.datetime()`

### 9. 커밋 시점 위임

> 커밋은 너가 할 타이밍을 추천해서 나한테 물어봐 허락을 하면 커밋해

기능 단위가 끝나고 검증이 통과한 지점에서 커밋 계획을 먼저 제안하고, 승인 후 실행하는 방식으로 전환.

### 10. Supabase 연동

> Supabase 연결 진행해줘

작업 중 스키마 버그를 발견해 함께 수정했다.
중복 방지에 쓰던 부분 유니크 인덱스는 `on conflict` 가 자동으로 추론하지 못해 upsert가 실패한다.
일반 UNIQUE 제약으로 바꿔도 PostgreSQL이 NULL을 서로 다른 값으로 취급하므로 원래 의도는 그대로 유지된다.

### 11. 프로젝트 생성 시 보안 설정

> new project 할때 security 설정은 어떻게 해? Enable Data API / Automatically expose new tables / Enable automatic RLS

셋 다 켜는 것으로 안내. "노출(expose)"이 "공개(public)"로 오해되기 쉬워 설명을 문서에 추가했다.
노출은 API 문 앞까지 도달 가능하다는 뜻이고, 실제 접근 여부는 RLS가 결정한다.

### 12. 젠레스 존 제로 데이터 출처 조사

> 젠레스 존 제로 API 파라미터 찾아줘

호스트 8개, 경로 10개 이상을 시도했으나 ZZZ에는 `getAnnList` 공지 API가 없다는 결론.
대안으로 HoYoLAB 뉴스 API를 찾았고, 버전 기간표를 이용해 상대 날짜 표현을 치환하면
LLM 없이 기간 추출이 가능하다는 것을 실측으로 확인했다.

### 13. 하이드레이션 경고

> 사이트에서 (하이드레이션 불일치 콘솔 에러) 이런 오류가 있어

`data-hwp-extension` 속성을 브라우저 확장이 `<html>` 에 주입해 생긴 문제였다.
`suppressHydrationWarning` 으로 해결. 이 속성은 자식으로 전파되지 않아 실제 버그를 가리지 않는다.

### 14. 니케 · 명조 수집기

> 응 크롤러 진행해줘

두 게임 모두 "크롤링해야 하는 게임"으로 분류돼 있었으나, 실제로 확인해 보니 JSON API가 있었다.
명조는 공식 사이트가 CDN의 정적 JSON을 읽어 화면을 그리고, 니케는 레벨 인피니트 CMS API를 쓴다.
계획에 있던 LLM 파서는 필요 없어졌고, `crawler` 수집 방식 자체를 레지스트리에서 없앴다.

작업 중 세 가지를 물어 결정했다.

- 니케는 공지 하나가 일정 수십 건으로 펼쳐진다(공지 20건 → 일정 112건, 전체의 38%).
  픽업 · 복각 · 이벤트 · 콜라보만 담기로 해 44건으로 줄였다.
- 수집량이 늘어 메인 페이지 조회를 최근 3개월 + 미래 전체로 제한했다. 과거 데이터는 DB에 그대로 남는다.
- 니케 본문에는 구획별 이미지가 없어 카드 여러 장이 같은 배너를 공유했다. 배너를 빼기로 했다.

가장 오래 잡고 있던 버그는 정규식 캡처 그룹 문제였다.
날짜만 캡처하는 패턴에 날짜+시각 여섯 그룹을 읽는 함수를 쓰는 바람에, 시각 자리에 종료일의 연도가
들어가 예외가 났고, 그 예외를 삼키는 코드 때문에 조용히 다음 패턴으로 떨어졌다.
겉으로는 "종료일이 없는 일정 87건"으로만 보였다. 함수를 `matchToUtcIso` / `matchDateToUtcIso` 로
갈라 같은 실수를 다시 할 수 없게 만들었다.
