### 4. 데이터 수집 방식에 대한 문제 제기

> 게임 픽업과 스케쥴 일정을 API로 못불러오는거 아니야? 이 문제는 해결하기 위해 내 답변 보고 다시 물어봐줘

**이 지적이 설계를 바꿨다.**

레퍼런스 사이트가 크롤링을 쓴다는 이유로 크롤링을 전제하고 있었으나,
실제로 후보 엔드포인트를 호출해 검증한 결과 공식 API가 존재했다.

| 게임 | 검증 결과 |
|---|---|
| 원신 | HTTP 200 — 시작일·종료일·배너까지 구조화 제공 |
| 붕괴: 스타레일 | HTTP 200 — 동일 스키마 |
| 림버스 컴퍼니 | HTTP 200 — Steam 공식 Web API |
| 젠레스 존 제로 | 게이트웨이 호스트 미확정 |
| 니케 / 명조 | 공개 API 없음 |

"모든 공지를 LLM으로 파싱한다"는 초기 계획은 과잉 설계였고,
LLM 파서가 필요한 범위가 6종 중 2종으로 축소됐다.

### 10. Supabase 연동

> Supabase 연결 진행해줘

작업 중 스키마 버그를 발견해 함께 수정했다.
중복 방지에 쓰던 부분 유니크 인덱스는 `on conflict` 가 자동으로 추론하지 못해 upsert가 실패한다.
일반 UNIQUE 제약으로 바꿔도 PostgreSQL이 NULL을 서로 다른 값으로 취급하므로 원래 의도는 그대로 유지된다.

### 11. 프로젝트 생성 시 보안 설정

셋 다 켜는 것으로 안내. "노출(expose)"이 "공개(public)"로 오해되기 쉬워 설명을 문서에 추가했다.

### 14. 니케 · 명조 수집기

> 응 크롤러 진행해줘

두 게임 모두 "크롤링해야 하는 게임"으로 분류돼 있었으나, 실제로 확인해 보니 JSON API가 있었다.
명조는 공식 사이트가 CDN의 정적 JSON을 읽어 화면을 그리고, 니케는 레벨 인피니트 CMS API를 쓴다.
계획에 있던 LLM 파서는 필요 없어졌고, `crawler` 수집 방식 자체를 레지스트리에서 없앴다.

작업 중 세 가지를 물어 결정했다.

- 니케는 공지 하나가 일정 수십 건으로 펼쳐진다(공지 20건 → 일정 112건, 전체의 38%).
  픽업 · 복각 · 이벤트 · 콜라보만 담기로 해 44건으로 줄였다.
- 수집량이 늘어 메인 페이지 조회를 최근 3개월 + 미래 전체로 제한했다. 과거 데이터는 DB에 그대로 남는다.
- 니케 본문에는 구획별 이미지가 없어 카드 여러 장이 같은 배너를 공유했다. 배너를 빼기로 했다.

가장 오래 잡고 있던 버그는 정규식 캡처 그룹 문제였다.
날짜만 캡처하는 패턴에 날짜+시각 여섯 그룹을 읽는 함수를 쓰는 바람에, 시각 자리에 종료일의 연도가
들어가 예외가 났고, 그 예외를 삼키는 코드 때문에 조용히 다음 패턴으로 떨어졌다.
겉으로는 "종료일이 없는 일정 87건"으로만 보였다. 함수를 `matchToUtcIso` / `matchDateToUtcIso` 로
갈라 같은 실수를 다시 할 수 없게 만들었다.

상세 조사 기록은 [조사-니케-명조-데이터-출처.md](조사-니케-명조-데이터-출처.md) 참고.

### 16. 미완성 수집 로직 개선

> 미완성 수집 로직 개선해줘

`CLAUDE.md` 의 "알려진 미완성 부분"에 적힌 세 가지를 손봤다.
고치기 전에 [`scripts/diagnose-periods.ts`](../scripts/diagnose-periods.ts) 를 만들어 실제 공지 원문을 먼저 봤다.
정규식을 늘리는 일은 추측으로 하면 오탐만 는다.

확인해 보니 셋 중 하나는 아예 문제가 아니었고, 하나는 근거가 없었으며,
나머지 하나는 예상과 다른 곳이 문제였다.

**명조 — 오차가 없었다.** 같은 이벤트를 `(서버 시간) 10:00` 과 `(한국 시간) 11:00` 로
나란히 적은 줄을 찾았고, 점검을 서버 시간으로 적은 공지는 `04:00` 으로 적는다는 것도 확인했다.
버전 점검이 늘 `05:00` 인 것은 한국시간 하루 경계에 맞춘 값이다.
"최대 1시간 오차 가능" 경고는 근거 없는 자기 경고였으므로 지우고, 대신 판단 근거를 주석과
조사 문서에 남겼다. 다음에 이 코드를 보는 사람이 다시 의심하지 않도록.

**니케 — 확정 근거가 없어 하한을 올렸다.** 점검 안내 공지를 찾으려고 공지 컬럼 두 개를
30건씩 훑었지만 점검 안내 자체가 API에 없었다. 업데이트 공지는 점검 사흘 전에 올라와
게시 시각도 근거가 못 됐다. 다만 니케의 모든 일정이 `5:00:00` 시작 · `4:59:59` 종료라
하루 경계가 05:00이고, 점검은 그 뒤에 시작하므로 종료는 반드시 05:00보다 늦다.
그래서 그날 0시 대신 05:00을 쓰기로 했다. 실제보다 이르다는 성질은 지키면서 오차만 다섯 시간 줄었다.

**젠레스 — 놓치던 표기 둘을 찾았다.** 기간을 못 뽑은 5건을 전부 열어 보니
셋은 진짜 기간이 없는 글(이슈 안내 · FAQ · 최적화)이었고, 둘은 읽을 수 있는데 놓치고 있었다.

- `3.1 버전 업데이트 후 … 영구 개방` → 시작은 버전 시작
- `2026/07/04 01:00:00(KST) 이후` → 그 시각이 시작

둘 다 게시일을 대신 쓰고 있었다. 고친 뒤 `신규 스토리: 메인 스토리 시즌 3 제2장` 의 시작이
3.1 버전 시작(사전 다운로드 공지의 점검 종료 시각)과 일치하는 것으로 검증했다.

수집 결과: 젠레스에서 게시일로 때우던 공지가 5건 → 2건, 니케 32건의 시작이 0시 → 05:00.
전체 건수(185건)와 실패 건수(0건)는 그대로다. 목 데이터에서 실제로 바뀐 값은 `startAt` 35건뿐이다.
